数据库系统判断/选择题概念总结

下载 PDF离线 / 打印版

说明：以下内容按“容易出判断题/选择题”的方式整理，尽量写成可直接判断对错的陈述句；以 1.md 到 15.md 为主，未使用 html 补充，因为 md 内容已足够清晰。文中高频专有名词尽量补成“中文（English）”格式。

1. 绪论

  • 数据库（database）是一个相互关联的、有组织的数据集合；数据库管理系统（database management system, DBMS）是管理数据库的软件，二者不是同一个概念。
  • 数据库系统的核心通常是数据本身，而不是执行计算的程序。
  • 在线事务处理（online transaction processing, OLTP）通常以短事务、简单查询、少量数据访问为主，且写操作往往比在线分析处理（online analytical processing, OLAP）更多。
  • 在线分析处理（online analytical processing, OLAP）通常以长时间运行、复杂聚合查询和大范围读取为主。
  • 文件系统（file system）容易出现数据冗余（redundancy）和不一致（inconsistency），而 DBMS 的目标之一就是缓解这些问题。
  • 文件系统很难良好地处理完整性约束（integrity constraints）、原子性（atomicity）、并发访问异常（concurrent-access anomalies）和安全控制（security control）。
  • 数据模型（data model）用于描述数据、关系、语义和一致性约束。
  • 关系模型（relational model）是最广泛使用的数据模型之一。
  • 数据抽象（data abstraction）使用户不必关心数据在底层是如何存储和组织的。
  • 数据独立性（data independence）指用户/应用与低层数据表示相隔离。
  • 结构化查询语言（Structured Query Language, SQL）属于声明式语言（declarative language），说明“要什么”，而不是“怎么做”。
  • 非过程型查询语言（nonprocedural query language）通常不具备通用编程语言那样的图灵完备能力。
  • 物理设计（physical design）通常包括索引（indexing）、聚类（clustering）和数据库调优（tuning）。
  • DBMS 的恢复管理器（recovery manager）负责在系统或事务故障后帮助数据库回到一致状态。

2. 关系模型与关系代数

  • 关系（relation）是元组（tuple）的无序集合，因此关系中元组顺序没有语义意义。
  • 同一个关系中不能有重复元组。
  • 属性（attribute）的域（domain）是该属性允许取值的集合。
  • 第一范式（First Normal Form, 1NF）要求属性值具有原子性（atomicity）。
  • 多值属性（multivalued attribute）和复合属性（composite attribute）都不满足原子性要求。
  • null 是所有域的成员，但会让很多运算的定义变复杂。
  • 关系模式（relation schema）描述结构，关系实例（relation instance）描述某一时刻的数据快照（snapshot）。
  • 超键（superkey）能够唯一标识元组，但不一定是最小的。
  • 候选键（candidate key）是最小超键。
  • 主键（primary key）是被设计者选中的候选键。
  • 主键不一定只包含一个属性。
  • 外键（foreign key）值必须要么在被参照关系（referenced relation）中存在，要么为 null。
  • 在本套笔记中，外键默认参照被参照关系的主键。
  • 约束（constraint）是所有合法数据库实例都必须满足的条件。
  • 关系代数（relational algebra）是基于集合代数（set algebra）的查询语言。
  • 选择运算（selection）只保留满足谓词（predicate）的元组，不改变属性集合。
  • 投影运算（projection）只保留指定属性，并会去除重复元组。
  • 笛卡尔积（Cartesian product）会组合两个关系中的每一对元组。
  • 自然连接（natural join）要求两个关系存在同名且可兼容的公共属性。
  • 自然连接只保留公共属性值相等的元组。
  • 集合并（union）、交（intersection）、差（difference）要求两个关系可兼容。
  • 关系可兼容（compatible）通常要求属性个数相同，且对应属性类型兼容。
  • 外连接（outer join）会保留连接条件不匹配的元组，并用 null 补齐缺失部分。
  • 左外连接（left outer join）保留左边关系的所有元组。
  • 右外连接（right outer join）保留右边关系的所有元组。
  • 全外连接（full outer join）可看作左外连接和右外连接结果的并集。
  • 删除操作一次只能删除整个元组，不能只删除元组中的某个属性。

3. SQL 基础

  • SQL 不仅能查询数据，也能定义模式（schema）、修改数据、定义视图（view）和授权（authorization）。
  • 数据定义语言（data-definition language, DDL）用于定义模式、约束、索引等结构。
  • 数据操纵语言（data-manipulation language, DML）用于查询和修改元组。
  • char(n) 是定长字符串（fixed-length string），varchar(n) 是变长字符串（variable-length string）。
  • 比较 char 和 varchar 时，结果可能受尾部空格处理方式影响。
  • NULL 适用于所有数据类型，除非显式禁止。
  • 声明主键后，该属性自动具备非空（not null）和唯一（unique）性质。
  • SQL 关键字通常大小写不敏感。
  • WHERE 子句（clause）用于过滤元组。
  • ORDER BY 用于排序（ordering），不改变查询结果的逻辑内容，只改变输出顺序。
  • 关系理论中通常不保留重复元组，但 SQL 默认按多重集（multiset）语义工作。
  • SQL 中如需去重，通常使用 DISTINCT。
  • 不能使用 = NULL 判断空值。
  • 判断空值应使用 IS NULL 或 IS NOT NULL。
  • 聚合函数（aggregate function）将一组值映射为单个值。
  • SUM 和 AVG 要求输入必须是数值类型。
  • 聚合函数不能直接出现在 WHERE 子句中。
  • GROUP BY 按分组属性（grouping attributes）对元组进行分组。
  • 在 SELECT 子句中，凡是不在聚合函数内部的属性，必须出现在 GROUP BY 中。
  • HAVING 是针对分组结果的过滤，而 WHERE 是针对分组前元组的过滤。
  • 在 HAVING 子句中，凡是不在聚合函数内部的属性，也必须出现在 GROUP BY 中。
  • EXISTS 判断子查询（subquery）结果是否非空。
  • UNIQUE 子查询用于判断是否不存在重复元组。
  • WITH 子句定义公共表表达式（common table expression, CTE），可视作临时命名结果。
  • 删除语句只能删除完整元组，不能只删除某列的值。
  • 窗口函数（window function）不会像聚合函数那样把多行压缩成一行。

4. 中级 SQL

  • NATURAL JOIN 会按所有同名属性相等进行连接，并只保留一份同名属性。
  • JOIN ... USING 比自然连接更可控，因为可以指定参与匹配的同名属性。
  • JOIN ... ON 比 USING 更通用，因为它支持任意连接谓词。
  • 内连接（inner join）不会保留连接条件不匹配的元组。
  • 外连接会保留未匹配元组，并用 null 填补未匹配的一侧。
  • 在外连接中，ON 与 WHERE 的作用并不完全等价。
  • 普通视图（view）通常只保存定义，不保存查询结果。
  • 物化视图（materialized view）会保存查询结果。
  • 当基表（base table）改变时，物化视图必须维护（maintenance）更新。
  • 视图更新并不总是可行。
  • 含有 GROUP BY 或 HAVING 的视图通常不可更新。
  • 事务（transaction）是一组 SQL 语句构成的工作单元。
  • COMMIT 会提交事务的更新。
  • ROLLBACK 会撤销事务中已执行的更新。
  • 完整性约束（integrity constraints）的目标是防止合法用户破坏数据库一致性。
  • NOT NULL 约束禁止属性取 null。
  • UNIQUE 约束要求指定属性组合在不同元组中互异。
  • CHECK 约束要求每个元组满足给定谓词。
  • 参照完整性（referential integrity）通常由外键实现。
  • 外键默认参照被参照关系的主键；若显式指定，也可参照被声明为 UNIQUE 的超键。
  • 外键允许为 null，除非额外声明 NOT NULL。
  • 外键两边的属性必须在数量和类型上兼容。
  • ON DELETE CASCADE 会在删除被参照元组时级联（cascade）删除参照元组。
  • ON UPDATE CASCADE 会在被参照键更新时同步更新参照方外键值。
  • 链式外键依赖可能使级联删除/更新沿整条链传播。
  • 断言（assertion）用于表达数据库始终应满足的全局条件。
  • COALESCE 返回参数列表中第一个非空值。
  • COALESCE 的参数应是相同类型或可兼容类型。
  • 用户自定义类型（user-defined type, UDT）即使底层类型相同，也可能被视为不同类型。
  • 生成列（generated column）或系统生成键（system-generated key）未必允许用户手工赋值，取决于声明方式。
  • 索引（index）是物理模式（physical schema）的一部分，不属于逻辑模式（logical schema）。
  • 索引是冗余结构（redundant structure），不影响数据库逻辑正确性，但影响性能和约束实现效率。
  • 索引可以建立在多个属性上。
  • 数据库不一定总能自动为你选择最佳索引。
  • GRANT 用于授予权限（privilege），REVOKE 用于撤销权限。
  • 权限可以通过角色（role）管理。
  • 被撤销的权限可能引发级联撤销（cascading revoke）。

5. 高级 SQL 与宿主语言接口

  • 预备语句（prepared statement）能减少 SQL 注入（SQL injection）风险。
  • 在预备语句中，参数占位符通常写作 ?。
  • Python 数据库程序默认不一定自动提交事务。
  • 存储过程（stored procedure）可以有输入参数（input parameter）和输出参数（output parameter）。
  • 函数（function）通常返回一个值；过程（procedure）更强调执行动作。
  • 触发器（trigger）是由数据库在特定事件发生时自动执行的语句。
  • 触发器常用于维护派生数据（derived data）、审计（audit）或复杂约束。
  • 触发器不是所有逻辑的最佳实现手段，滥用会增加系统复杂度。
  • 大对象（large object, LOB）通常不直接完整嵌入普通记录中，而是通过定位器（locator）等方式访问。

6. E-R 模型

  • 不良设计可能导致冗余（redundancy）和不完整性（incompleteness）。
  • 冗余会增加更新异常（update anomaly）和不一致（inconsistency）风险。
  • 二元联系（binary relationship）最常见，但并非所有场景都必须只用二元联系。
  • 映射基数（mapping cardinality）描述一个实体通过联系能够关联多少个另一侧实体。
  • 一对一（one-to-one）表示双方实体都至多关联对方一个实体。
  • 多对一（many-to-one）表示“多”的一侧每个实体至多关联“一”的一侧一个实体。
  • 多对多（many-to-many）表示双方都可关联任意数量的对方实体。
  • 完全参与（total participation）通常用双线表示，表示该实体集（entity set）中的每个实体（entity）都必须参加该联系（relationship set）。
  • 部分参与（partial participation）是默认情况。
  • 实体集中的键（key）概念与关系模型中的键概念基本一致。
  • 多对多联系集的主键通常是参与实体主键的并集。
  • 一对多或多对一联系集中，主键通常取“多”一侧实体的主键组合。
  • 一对一联系集中，任一侧主键都可能作为联系集主键。
  • 弱实体集（weak entity set）的存在依赖于识别实体集（identifying entity set）。
  • 弱实体集需要依靠识别实体集主键加自身判别属性（discriminator）来唯一标识。
  • 识别联系（identifying relationship）是从弱实体集到识别实体集的多对一联系。
  • 弱实体集必须完全参与其识别联系。
  • 识别联系不应再带独立描述属性（descriptive attribute），否则这些属性更应属于弱实体本身。
  • 将 E-R 图（E-R diagram）转换为关系模式时，强实体（strong entity）通常直接变成一个关系。
  • 多值属性通常要单独拆成关系模式。
  • 弱实体转换后的关系模式主键通常为“强实体主键 + 判别属性”。
  • 联系集转换为关系模式后，需要对每个参与实体建立外键约束。
  • 在某些多对一且完全参与的情况下，可以把联系关系并入实体关系中。
  • 特化（specialization）是自顶向下地把一个实体集拆成多个子实体集。
  • 泛化（generalization）是自底向上地把多个实体集抽象为更高层实体集。
  • 泛化本质上可看作特化的逆过程。
  • 低层实体集会继承高层实体集的属性继承（attribute inheritance）。
  • 低层实体集也会继承高层实体集参与联系的性质，这可看作参与继承（participation inheritance）。
  • 重叠特化（overlapping specialization）允许一个实体同时属于多个子类。
  • 互斥特化（disjoint specialization）要求一个实体至多属于一个子类。
  • 完全特化（total specialization）要求高层实体必须属于至少一个低层实体集。
  • 部分特化（partial specialization）允许有些高层实体不属于任何低层实体集，这也是默认情况。
  • 聚合（aggregation）把联系当作更高层对象看待，以便它再参与其他联系。
  • 把别的实体主键直接当成某实体的普通属性，往往意味着隐式联系（implicit relationship）和冗余。
  • 对象简单且只需记录一个值时，更适合建模为属性。
  • 对象包含较多独立信息时，更适合建模为实体集。
  • n 元联系（n-ary relationship）有时比拆成多个二元联系更清晰，也更能表达约束。

7. 关系数据库设计与规范化

  • 规范化（normalization）的目标之一是减少冗余和更新异常。
  • 分解（decomposition）是把一个大关系模式拆成更小的关系模式。
  • 分解不一定总是好的，因为可能出现有损分解（lossy decomposition）。
  • 无损分解（lossless decomposition）要求把分解后的关系自然连接起来，能够恢复原关系且不引入伪元组（spurious tuple）。
  • 函数依赖（functional dependency, FD）是建立范式理论的基础。
  • 若对任意元组对，只要左侧属性相等就能推出右侧属性相等，则满足函数依赖。
  • 某个实例满足某个函数依赖，不代表该依赖在整个关系模式上有效。
  • 若 K -> R 有效，则 K 是超键。
  • 平凡函数依赖（trivial functional dependency）指右侧属性集包含于左侧属性集。
  • BCNF（Boyce-Codd Normal Form）要求每个非平凡函数依赖的左侧都是超键。
  • 只有两个属性的关系模式一定满足 BCNF。
  • BCNF 能更强地消除冗余，但分解后不一定依赖保留（dependency preservation）。
  • 依赖保留指分解后各子关系上的依赖合起来仍能推出原依赖集合。
  • 3NF（Third Normal Form）比 BCNF 更弱，因此更容易做到依赖保留。
  • 3NF 允许某些左侧不是超键的依赖存在，但右侧属性必须是主属性（prime attribute）。
  • 在 BCNF 与依赖保留不可兼得时，课程笔记倾向于优先考虑 BCNF。
  • 1NF（First Normal Form）要求所有属性域具备原子性。
  • 对关系数据库而言，所有关系都必须满足 1NF。
  • Armstrong 公理（Armstrong's axioms）是推导函数依赖闭包（closure）的基础规则。
  • 属性闭包（attribute closure）可用于判断某属性集是否为超键。
  • 判断 α -> β 是否成立，可检查 β 是否包含于 α+。
  • 正则覆盖（canonical cover）与原依赖集逻辑等价，但更简洁。
  • 正则覆盖中不应含有多余属性（extraneous attribute）。
  • 删除函数依赖左侧属性会使约束更强。
  • 删除函数依赖右侧属性会使约束更弱。
  • 依赖保留是分解的理想性质，但不是所有 BCNF 分解都具备。
  • 多值依赖（multivalued dependency, MVD）比函数依赖更一般。
  • 所有函数依赖都是多值依赖。
  • 4NF（Fourth Normal Form）用于处理多值依赖带来的冗余问题。
  • 若一个模式中存在非平凡多值依赖，且左侧不是超键，则该模式违反 4NF。
  • 反规范化（denormalization）可能提升性能，但会增加冗余与维护复杂度。
  • 理想的命名设计倾向于让每个属性名只有一个明确含义。

8. 物理存储系统

  • 闪存（flash memory）是非易失性存储器（non-volatile storage），断电不会丢失数据。
  • 固态硬盘（solid-state drive, SSD）通常比机械磁盘（hard disk drive, HDD）更擅长随机访问。
  • 闪存页不能像普通内存那样直接覆盖写，通常需要擦除（erase）后重写。
  • 擦除是以块（block）为单位进行的，而不是以单页（page）随意进行。
  • RAID（redundant arrays of independent disks）的两个核心目标是提升可靠性（reliability）和提升性能（performance）。
  • 镜像（mirroring）通过冗余副本提升可靠性。
  • 镜像能容忍一个副本失效，只要另一个副本仍可用。
  • 数据分条（striping）可提升并行访问（parallel access）性能，但分条本身不提高可靠性。
  • RAID 0 只有分条，没有冗余，因此不提高可靠性。
  • RAID 1 是镜像，可靠性高，但成本较高。
  • RAID 5 使用分布式奇偶校验（distributed parity），适合读多写少。
  • RAID 6 比 RAID 5 冗余更多，可容忍两个磁盘故障。
  • RAID 不能抵抗火灾、洪水等站点级灾难（site-level disaster）。
  • RAID 仍可能出现潜在故障（latent failure）或 bit rot。
  • 擦洗（scrubbing）有助于发现并修复潜在介质错误。
  • 超前读取（read-ahead）在顺序访问中更有用，在随机访问中效果有限。

9. 存储结构与缓冲区

  • 页（page）是 DBMS 磁盘 I/O 和缓冲管理（buffer management）的基本单位。
  • 一个页里通常不混放多种类型的数据。
  • 槽式页（slotted page）要求指针先指向槽目录（slot directory），再间接定位记录（record）。
  • 这种间接寻址有助于记录在页内移动时保持外部引用稳定。
  • 堆文件（heap file）允许记录放在任意位置。
  • 堆文件中记录一旦放定位置，通常不希望频繁移动。
  • 顺序文件（sequential file）按搜索键（search key）物理有序存储，适合顺序处理。
  • 顺序文件随着插入增多会逐渐退化，可能需要重组织（reorganize）。
  • 多表聚集文件组织（multitable clustering file organization）会把相关关系的记录放在同一块中，以减少连接代价。
  • 数据字典（data dictionary）存储的是元数据（metadata），而不是普通业务数据本身。
  • 数据字典通常记录关系模式、存储组织和索引等信息。
  • 页表（page table）是缓冲池（buffer pool）中的内存哈希表（hash table），用于把页 ID 映射到缓冲帧（buffer frame）。
  • 读取页前通常需要先将该页钉住（pin），防止被驱逐（evict）。
  • 只有当钉计数（pin count）降为 0 时，该页才能被驱逐。
  • 对数据块进行更新前，需要独占锁（exclusive lock）；读取前需要共享锁（shared lock）。
  • 最近最少使用（least recently used, LRU）并非所有查询模式下都最佳。
  • 在某些扫描模式下，最近最多使用（most recently used, MRU）可能比 LRU 更合适。
  • 日志文件系统（journaling file system）通过写日志来避免代价高昂的一致性检查。
  • 缓冲池旁路（buffer pool bypass）适合顺序扫描或临时数据，避免污染缓存池。
  • 列式存储（column-oriented storage）适合只访问少量列和执行聚合的分析型负载。
  • 压缩（compression）在数据库中通常要求无损（lossless）。
  • 主存数据库（main-memory database）把数据主要存于内存，以换取更高访问性能。

10. 索引

  • 顺序索引（ordered index）按搜索键顺序存储索引项。
  • 聚集索引（clustering index / primary index）要求数据文件顺序与搜索键顺序一致。
  • 二级索引（secondary index）不要求文件物理顺序与索引键顺序一致。
  • 稠密索引（dense index）对每个搜索键值都有索引项。
  • 稀疏索引（sparse index）只对部分搜索键值建立索引项。
  • 稀疏索引通常依赖数据文件本身按搜索键有序。
  • 多级索引（multilevel index）本质上是在索引之上再建索引。
  • 多级索引可以显著减少查找所需 I/O。
  • 二级索引能改善按非聚集键查询的性能，但会增加更新代价。
  • B+ 树（B+ tree）是平衡树（balanced tree），因此从根到各叶子的路径长度相同。
  • B+ 树的非叶子节点（nonleaf node）用于导航，叶子节点（leaf node）存储实际索引项。
  • B+ 树叶子节点通常按搜索键顺序链接，便于范围扫描（range scan）。
  • B+ 树支持等值查询（equality search）和范围查询（range query）。
  • 哈希索引（hash index）适合等值查询，不适合范围查询。
  • B+ 树插入可能引起节点分裂（split）。
  • B+ 树删除可能引起节点下溢（underflow）、合并（merge）或重分配（redistribution）。
  • B+ 树内部节点中的键值可能出现在叶子中多次。
  • B 树（B tree）与 B+ 树不同，B 树的搜索键通常只存一份。
  • 实践中数据库系统通常更偏好 B+ 树而不是 B 树。
  • 在 B+ 树文件组织（B+ tree file organization）中，真实记录放在叶子节点中。
  • 若二级索引直接存物理记录指针，则记录搬迁可能迫使大量二级索引更新。
  • 为减少这种代价，二级索引有时存一级索引键而不是物理地址。
  • 批量加载（bulk loading）适合一次性构建大索引，比逐条插入更高效。
  • 覆盖索引（covering index）除了搜索键外还保存额外属性，可减少回表。
  • 哈希冲突（hash collision）可通过溢出桶（overflow bucket）/溢出链（overflow chaining）处理。
  • 静态哈希（static hashing）桶数固定，记录数增长后可能退化。
  • 动态哈希（dynamic hashing）允许桶数增长，如线性哈希（linear hashing）和可扩展哈希（extendible hashing）。
  • 哈希函数（hash function）需要权衡计算速度和冲突概率。
  • 位图索引（bitmap index）适合低基数（low cardinality）属性上的组合条件查询。
  • 位图索引常通过按位与（bitwise AND）、或（bitwise OR）等位运算实现多条件过滤。
  • LSM 树（log-structured merge tree, LSM tree）适合写多场景。
  • 缓冲区树（buffer tree）相较 LSM 树通常更偏向读优化。
  • 写多读少时，LSM 树往往比缓冲区树更合适。

11. 查询处理

  • 文件扫描（file scan）是最底层的数据访问方式之一。
  • 线性扫描（linear scan）不依赖索引，但通常代价较高。
  • 索引扫描（index scan）依赖可用索引。
  • 二级索引做范围查询时，若命中记录很多，随机 I/O 代价会很高。
  • 复杂选择可以通过单索引、复合索引（composite index）或标识符（RID）集合并/交来实现。
  • 当内存装不下全部数据时，需要外部排序（external sorting）。
  • 外部排序-归并（external sort-merge）通常先生成顺串（run），再多路归并（multiway merge）。
  • 聚集 B+ 树顺序扫描有时可直接产生排序结果。
  • 嵌套循环连接（nested-loop join）适用于最一般的连接条件，但通常不够高效。
  • 块嵌套循环连接（block nested-loop join）通过按块读取外层关系降低 I/O。
  • 索引嵌套循环连接（indexed nested-loop join）在内层连接属性有索引时很有效。
  • 归并连接（merge join）通常要求输入在连接属性上有序。
  • 哈希连接（hash join）通常适用于等值连接（equi-join）。
  • 哈希连接通过把两个输入按相同哈希函数分区（partition），只比较对应分区。
  • 去重（duplicate elimination）可通过排序或哈希实现。
  • 聚合也可通过排序或哈希实现。
  • 物化求值（materialized evaluation）会把中间结果写入临时关系。
  • 流水线求值（pipelined evaluation）会把一个算子的输出直接交给下一个算子。
  • 物化会增加中间结果写盘成本。
  • 流水线有助于更快产出结果并减少中间结果落盘。
  • 不是所有算子都适合完全流水线化。
  • 哈希连接通常包含阻塞阶段（blocking phase），因为要先完成分区或构建（build）。
  • 外部排序本身也是阻塞型操作（blocking operation）。

12. 查询优化

  • 查询优化（query optimization）的目标是在等价执行计划（execution plan）中选成本最低的方案。
  • SQL 是声明式语言，因此优化器（optimizer）必须决定“如何执行”。
  • 优化可基于等价规则（equivalence rules），也可基于成本估计（cost estimation）。
  • 选择运算满足交换律（commutativity）。
  • 合取选择（conjunctive selection）可拆成多个选择串联执行。
  • 当选择条件只涉及一个输入关系的属性时，选择可下推（push down）到连接之前。
  • 尽早做选择通常能减少后续连接代价。
  • 选择在满足条件时可下推到聚合、并、交、差等运算之前。
  • 连接顺序（join order）会显著影响执行代价。
  • 连接顺序数量增长非常快，通常不能暴力穷举全部情况。
  • 动态规划（dynamic programming）是常见的连接顺序选择方法。
  • 左深连接树（left-deep join tree）常见于实际优化器，因为便于流水线化。
  • 成本估计依赖目录统计信息（catalog statistics）。
  • 若缺少直方图（histogram），通常会假设值均匀分布（uniform distribution）。
  • 选择结果大小估计常依赖属性不同值个数 V(A, r)。
  • 连接结果大小估计通常依赖连接属性的不同值统计。
  • 计划缓存（plan caching）会复用先前生成的执行计划，即使新的常量值可能使最优计划变化。
  • 启发式优化（heuristic optimization）通常不会穷尽所有等价计划。
  • 子查询去相关（decorrelation）并不总是可行，涉及聚合时常更困难。
  • 物化视图存储查询结果，因此本质上是冗余数据。
  • 物化视图能显著降低重复查询的代价。
  • 物化视图必须维护；完全重算（full recomputation）不是唯一维护方式。
  • 增量视图维护（incremental view maintenance）只更新受影响部分。
  • AVG 的增量维护通常依赖同时维护 SUM 和 COUNT。
  • MIN 和 MAX 的增量删除维护通常比 SUM/COUNT 更麻烦。

13. 事务基础

  • 事务（transaction）是数据库中执行的基本逻辑工作单位。
  • 原子性（atomicity）要求事务要么全部完成，要么完全不产生效果。
  • 一致性（consistency）要求事务执行前后数据库满足一致性约束。
  • 隔离性（isolation）要求并发事务看起来像串行执行。
  • 持久性（durability）要求已提交事务的效果在故障后仍然存在。
  • 原子性通常依赖恢复系统和日志机制。
  • 中止（abort）事务的更新必须被回滚（rollback）。
  • 已提交事务不能再通过普通中止撤销。
  • 外部可观察写操作（observable external write）一旦发生，通常无法简单回滚。
  • 调度（schedule）必须保留每个事务内部操作的相对顺序。
  • 串行调度（serial schedule）一定是可串行化（serializable）的。
  • 可串行化调度（serializable schedule）并不一定是字面上的串行执行。
  • 冲突等价（conflict equivalence）要求两个调度中每对冲突操作的相对顺序一致。
  • 若某调度冲突等价于某个串行调度，则它是冲突可串行化（conflict serializable）的。
  • 优先图（precedence graph）无环是冲突可串行化的充分必要条件。
  • 若优先图有环，则该调度不是冲突可串行化的。
  • 可恢复调度（recoverable schedule）要求：若 Tj 读了 Ti 写的数据，则 Ti 必须先于 Tj 提交。
  • 不可恢复调度（unrecoverable schedule）会导致已提交事务依赖未提交事务，无法正确恢复。
  • 无级联调度（cascadeless schedule）要求事务只读取已提交事务写入的数据。
  • 所有无级联调度都是可恢复的。
  • 快照隔离（snapshot isolation）的只读事务通常不会等待，也不会被中止。
  • 快照隔离不保证可串行性。

14. 并发控制

  • 两阶段锁协议（two-phase locking, 2PL）要求先获取锁后释放锁，释放后不能再申请新锁。
  • 2PL 能保证冲突可串行化。
  • 冲突可串行化的调度不一定都来自 2PL。
  • 严格两阶段锁协议（Strict 2PL）要求所有独占锁（exclusive lock, X-lock）持有到提交。
  • Strict 2PL 能避免级联回滚（cascading rollback）。
  • 强严格两阶段锁协议（rigorous 2PL）要求所有锁都持有到提交。
  • 强严格 2PL 下，调度可按提交顺序串行化。
  • 锁升级（lock upgrade）和锁降级（lock downgrade）都必须遵守两阶段约束。
  • 树协议（tree protocol）能够保证冲突可串行化。
  • 树协议不要求满足两阶段锁协议。
  • 树协议的一个优点是不会发生死锁（deadlock）。
  • 多粒度锁协议（multiple-granularity locking protocol）依赖意向锁（intention lock）。
  • 意向锁使系统无需遍历整棵树即可判断上层节点能否加锁。
  • 多粒度锁通常要求加锁自顶向下，释放自底向上。
  • 多粒度锁协议本身不能保证没有死锁。
  • 锁升级（lock escalation）可用一个高层锁替代大量低层锁。
  • 幽灵现象（phantom phenomenon）是谓词读取（predicate read）下，由于并发插入/删除导致重复查询结果集变化。
  • 仅锁住已存在元组并不能完全防止幽灵现象。
  • 通过对索引加锁可以帮助消除幽灵现象。
  • Wait-die 是非抢占式（non-preemptive）死锁预防（deadlock prevention）方案。
  • 在 wait-die 中，老事务可以等待年轻事务，年轻事务请求老事务资源时会回滚。
  • Wound-wait 是抢占式（preemptive）死锁预防方案。
  • 在 wound-wait 中，老事务可“伤害”年轻事务并令其回滚。
  • 时间戳顺序协议（timestamp-ordering protocol）按时间戳顺序安排冲突操作。
  • 基本时间戳顺序协议不会产生死锁，因为事务不等待，只会回滚。
  • 基本时间戳顺序协议可能导致饥饿（starvation）。
  • 基本时间戳顺序协议本身不保证可恢复性和无级联性。
  • Thomas 写规则（Thomas' write rule）允许忽略某些过时写操作。
  • 所有冲突可串行化调度都是视图可串行化（view serializable）的。
  • 视图可串行化调度不一定是冲突可串行化的。
  • 出现盲写（blind write）时，视图可串行化不一定等于冲突可串行化。
  • 验证协议（validation protocol）属于乐观并发控制（optimistic concurrency control, OCC）。
  • 乐观并发控制假设冲突较少，失败通常在提交前验证阶段（validation phase）发现。
  • 乐观并发控制也可能导致长事务饥饿。
  • 多版本并发控制（multiversion concurrency control, MVCC）的关键优势是读通常不阻塞写，写通常不阻塞读。
  • 多版本时间戳排序（multiversion timestamp ordering）能确保可串行性。
  • 多版本时间戳排序不天然保证可恢复性和无级联性。
  • 多版本 2PL（multiversion 2PL）能确保可恢复性和无级联性。
  • 快照隔离为事务提供开始时刻的已提交数据快照。
  • 快照隔离下，事务只能看到开始前已提交的版本。
  • 快照隔离必须防止丢失更新（lost update）。
  • 快照隔离常见规则包括“先提交者胜”（first committer wins）和“先更新者胜”（first updater wins）。
  • 快照隔离非常适合长时间只读事务。
  • 快照隔离不保证可串行性，可能发生写偏斜（write skew）。
  • 快照隔离下，完整性约束应在提交时基于当前状态检查，而非仅基于快照检查。
  • 可串行化快照隔离（serializable snapshot isolation, SSI）通过跟踪读写冲突（read-write conflict）来恢复可串行性。
  • SQL 的 FOR UPDATE 在某些系统中可用于人为制造冲突以避免快照隔离异常。
  • 二级一致性（degree-two consistency）避免级联中止，但不保证可串行性。
  • 在二级一致性下，共享锁可提前释放，但独占锁要持有到提交或中止。
  • 游标稳定性（cursor stability）是一种面向游标（cursor）遍历程序的较弱一致性级别。
  • 跨用户交互的长事务通常不适合直接用传统 2PL、时间戳或快照隔离硬撑到底。
  • 对有用户交互的事务，拆分成多个短事务并配合版本号（version number）检查，通常更实用。

15. 恢复系统

  • 恢复算法（recovery algorithm）的目标是保证原子性和持久性，并在故障后恢复一致性。
  • 系统错误（system error）、磁盘故障（disk failure）和介质灾难（media disaster）都可能触发恢复机制。
  • 稳定存储（stable storage）是理论概念，现实中通过多副本近似实现。
  • RAID 不能替代异地备份，因为它无法抵御站点级灾难。
  • 远程备份（remote backup）可提升高可用性（high availability）与抗灾能力。
  • 日志（log）是恢复系统最核心的数据结构之一。
  • 更新日志（update log record）通常包含事务标识、数据项标识、旧值（old value）和新值（new value）。
  • 在修改数据库之前，必须先写对应日志记录。
  • 这就是写前日志（write-ahead logging, WAL）的核心思想之一。
  • undo 把数据恢复为旧值。
  • redo 把数据恢复为新值。
  • 若允许未提交事务更新过的数据被其他事务再更新，恢复会变复杂。
  • Strict 2PL 有助于简化恢复，因为它防止其他事务覆盖未提交事务修改的数据。
  • 延迟修改（deferred modification）在事务提交前不直接改数据库。
  • 立即修改（immediate modification）允许事务执行期间就改数据库页。
  • 日志中的提交记录写入稳定存储后，事务才算真正提交。
  • 已提交事务的数据页不必在提交时立刻写回磁盘。
  • 批量提交日志可以减少稳定存储写入开销。
  • redo 时必须保持原始更新顺序。
  • 回滚过程中可能会写补偿日志记录（compensation log record, CLR）。
  • CLR 通常是 redo-only 日志记录。
  • 简单检查点（checkpoint）常要求把脏页（dirty page）刷盘，并记录活跃事务（active transaction）。
  • 检查点的作用之一是缩短恢复时需要扫描的日志范围。
  • 模糊检查点（fuzzy checkpoint）允许事务在检查点期间继续执行。
  • 模糊检查点不要求在做检查点时强制把所有脏页都刷盘。
  • 模糊检查点通常要记录活跃事务表（active transaction table, ATT）和脏页表（dirty page table, DPT）。
  • WAL 要求在数据页写盘前，与该页相关的日志必须先落盘。
  • WAL 的另一条要求是事务提交前，其所有日志记录必须已落盘。
  • STEAL + NO-FORCE 是很多现代 DBMS 的常见缓冲策略（buffer management policy）组合。
  • STEAL 表示允许把未提交事务修改过的页写回磁盘，因此必须支持 undo。
  • NO-FORCE 表示提交时不强制把所有更新页写盘，因此必须支持 redo。
  • ARIES（Algorithms for Recovery and Isolation Exploiting Semantics）是经典恢复算法。
  • ARIES 使用日志序列号（log sequence number, LSN）标识日志记录。
  • 每个页面维护 PageLSN，表示该页已应用到的最新日志记录号。
  • 若某条日志的 LSN 小于等于页面的 PageLSN，则该日志通常无需再对该页重做。
  • ARIES 使用脏页表减少不必要的重做（redo）。
  • 脏页表中的 RecLSN 表示该页自上次刷盘以来最早的相关日志位置。
  • ARIES 的恢复分为分析（analysis）、重做（redo）、撤销（undo）三个阶段。
  • 分析阶段确定活跃事务和脏页信息。
  • 重做阶段从 RedoLSN 开始“重演历史”（repeating history）。
  • ARIES 的重做不仅重做已提交事务，也会重做当时未完成事务的历史操作。
  • ARIES 的撤销阶段会逆向扫描并回滚未完成事务。
  • 在 ARIES 中，CLR 也会参与恢复流程。
  • PrevLSN 让系统能沿着单个事务的日志链反向回溯。
  • UndoNextLSN 让系统在崩溃后继续未完成的撤销。
  • ARIES 支持生理日志（physiological logging），即“页物理、页内逻辑”的混合方式。
  • 远程备份站点接管前，也需要对接收到的数据和日志执行恢复。
  • “一级安全”“二级安全”“二级非常安全”体现的是主站点（primary site）与备份站点（secondary site）在提交确认上的不同严格程度。
