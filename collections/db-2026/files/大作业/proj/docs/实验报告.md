# MiniSQL 实验报告

>一个从零实现的精简型单用户关系型数据库引擎（C++17，对标 CMU 15-445 / BusTub）。
>本报告记录系统设计、各模块实现、关键问题与解决、以及测试验证。

---

## 一、实验目的与概述

实现一个支持 SQL 子集的单用户关系数据库引擎，覆盖 DBMS 的核心层次：

- **存储层**：磁盘按页读写、缓冲池与页置换、定长记录的堆表存储。
- **索引层**：B+ 树索引（单属性单值），支持等值与区间查询。
- **元数据层**：表/列/索引的数据字典及其持久化；多数据库管理。
- **语言层**：SQL 词法/语法解析、执行引擎将语句派发到各管理器。
- **Bonus**：Clock 置换、磁盘空闲页回收、两阶段封锁并发控制、WAL 崩溃恢复。

最终系统能在交互式 REPL 或批处理脚本下运行完整 SQL，并通过一份约 10 万条语句的验收脚本端到端验证。

**关键参数**：页大小 `PAGE_SIZE = 4096` 字节；单表最多 `MAX_COLUMNS = 32` 列；
缓冲池 `BUFFER_POOL_SIZE = 1024` 帧（约 4MB/库）；数据类型 `INTEGER`(4B) / `FLOAT`(4B) / `CHAR(n)`(n B)。

---

## 二、系统总体设计

采用严格分层架构，自底向上：

```
DiskManager → BufferPoolManager(+Replacer) → TableHeap / BPlusTree
            → CatalogManager / IndexManager → DatabaseEngine
            → ExecuteEngine → Interpreter → main(REPL/批处理)
```

**核心约定（分层铁律）**：除 `BufferPoolManager` 外，任何上层模块都不直接访问 `DiskManager`，
一律通过 `FetchPage / NewPage / UnpinPage / DeletePage` 操作页。这保证了缓存、脏页刷盘、
页置换的统一管理，是存储层解耦的关键。

每个被读取的页都遵循「Fetch → 读写 → Unpin（修改过则标脏）」的配对纪律，避免 pin 泄漏。

## 三、各模块设计与实现

### 3.1 DiskManager（磁盘管理）

以页为单位顺序读写数据库文件。`AllocatePage` 递增分配页号；重启时由文件大小恢复
下一个可分配页号；从未写过的页读出补零。`WritePage` 立即 `flush` 保证持久性。

**Bonus 空闲页回收**：维护 `free_list_` 栈，`DeallocatePage` 入栈、`AllocatePage` 优先复用；
空闲页清单持久化到 `<dbfile>.free` 旁车文件（避免在数据文件中预留元页），重开后继承。

### 3.2 BufferPoolManager + Replacer（缓冲池）

维护 `page_table_`(page_id→frame)、pin 计数、脏页刷盘，并委托 `Replacer` 做页置换。
`FindVictimFrame` 统一腾帧逻辑：先取空闲帧，否则向 Replacer 要牺牲帧，脏则先刷盘并清旧映射。

- **LRUReplacer**：`list + unordered_map<frame, iterator>` 实现 O(1) 的 Unpin/Pin/Victim。
- **ClockReplacer（Bonus）**：每帧一个 reference 状态（EMPTY / IN_USE_REF / IN_USE_NOREF），
  环形指针扫描，遇 REF 清零给「二次机会」，遇 NOREF 淘汰，近似 LRU 而开销更低。

注意 `~BufferPoolManager` **不自动刷脏页**，故新增 `FlushAllPages()` 供关库前显式调用。

### 3.3 记录与堆表（Record / TableHeap）

- **Value / Row**：`Value` 支持三类型的三路比较与定长序列化（CHAR 按列宽补零/截断）。
  `Row` 按 Schema 逐列连续排布序列化。序列化签名带 `len` 参数，CHAR 列宽由 Row 依 Schema 传入。
- **TableHeap**：表数据 = 数据页链表。页布局为 `[next_page_id | slot_count]` 页头 +
  「1 字节状态(0 空/1 占用) + 定长记录」槽序列。删除按槽标记，空间可被后续插入复用。
  支持惰性建首页（首次插入才分配数据页）。

  **优化**：缓存尾页 `last_page_id_`，插入直接追加到尾页（O(1) 摊还）。

### 3.4 B+ 树索引（BPlusTree / IndexManager）

单属性单值 B+ 树，key 为定长 `Value`、value 为记录 `RID`，节点持久化在缓冲池页上。

- **节点页布局**：公共头 `node_type | size`；叶子额外有 `next` 指针并存 `[key|rid]` 数组、
  串成链表支持区间扫描；内部节点存 key 数组 + child page_id 数组。
- **算法**：递归实现。`Insert` 叶层去重，溢出分裂（叶复制首键上推、内部中键上推），
  根分裂则新建内部根升高；`Remove` 下溢时优先向兄弟借位、否则合并，并处理根塌缩；
  `GetValue` 二分点查，`RangeScan` 沿叶链表收集 `[low, high]`。
- **几何**：fanout 由页大小自动计算，测试可传小扇出（如 4）以少量数据触发多级结构。
- **IndexManager**：管理索引生命周期，`GetIndex(table,col)` 供执行引擎选择走索引或全表扫描。

### 3.5 元数据与多库（CatalogManager / DatabaseEngine）

- **CatalogManager**：`CreateTable/DropTable/GetTable`；主键与 `unique` 列自动建 B+ 树索引。
  元数据（表名、schema、`first_page_id`、各索引名/列/根页号）序列化到固定的 **0 号目录页**，
  `LoadCatalog` 启动时解析重建。全新库通过 `NewPage` 自举 0 号页（用 `DiskManager::GetNumPages()`
  判断是否全新库），保证目录页稳定为 0 号、表数据页从 1 号起。
- **DatabaseEngine（多库）**：每个数据库一个独立 `.db` 文件 + 一套 Disk/BPM/Index/Catalog 存储栈；
  库名清单持久化到 `databases.meta`。`create/drop/use database`、`show databases`；关闭前 `FlushAll` 刷盘。

### 3.6 SQL 解释器（Interpreter）

手写词法 + 递归下降，无需完整语法分析器。词法识别 `--` 行注释、双引号串、复合操作符
（`<= >= <>`）、整数/浮点字面量；关键字大小写不敏感。按首关键字分派解析为 `Statement`（极简 AST）。
覆盖数据库命令、DDL、DML（含 `update`）、`where` 的 AND 条件链。

### 3.7 执行引擎与接线（ExecuteEngine / main）

`ExecuteEngine` 持有 `DatabaseEngine`，对「当前库」派发所有语句：

- **insert**：值按列类型强制（如整数写入 float 列）；对索引列做唯一性检查；写堆表后同步所有索引。
- **delete / update**：全表扫描 + `where` 过滤（`RowMatches` 用 `Value::CompareTo`）；
  维护索引；`update` 以「删旧 + 插新」实现（含改主键的情形）。
- **select**：扫描过滤后投影列并打印；结果经 `LastRows/LastColumns/LastAffected` 暴露以便测试。
- **DDL / 库级命令**：转交 Catalog / IndexManager / DatabaseEngine。

`main.cpp` 构造引擎并运行 REPL/批处理循环，按 `;` 切分语句（忽略字符串内 `;` 与 `--` 注释），
`isatty` 判断是否打印交互提示，支持从文件/管道批量执行。

### 3.8 Bonus：并发与恢复

- **LockManager（2PL + wound-wait）**：共享/排他锁，S-S 相容、X 互斥；2PL 下 `Unlock` 后进入
  SHRINKING 不得再申请锁。死锁预防用 **wound-wait**（按 `txn_id` 定优先级，小=老=高优先）：
  申请者更老则「创伤」（中止并强制释放）更年轻的持有者，更年轻则等待更老者——等待图只有
  「年轻→老」边、无环。实现用 `mutex + condition_variable`，多线程测试。
- **WAL 崩溃恢复**：`LogRecord` 自描述序列化（不依赖外部 schema）；`LogManager` 追加长度前缀的
  日志到独立日志文件并 `Flush`；`RecoveryManager` 解析日志，先 **Redo 全部**（重复历史）再对无
  COMMIT 的失败事务 **逆序 Undo**（插入→撤销、删除→恢复前像），重建出 `RID→Row` 状态。

>说明：LockManager 与 WAL 恢复是自包含的算法演示模块，未接入单用户引擎的实际读写路径
>（单用户无并发、未在写路径上挂日志）。

## 四、关键问题与解决

| 问题 | 现象 | 根因 | 解决 |
|------|------|------|------|
| B+ 树小扇出测试段错误 | 插入若干键后崩溃 | 内部节点键区只预留 `internal_max` 槽，「先插入后分裂」时临时溢出的第 `max+1` 个键正好覆盖孩子数组基址；叶子默认容量算满后溢出项越过页尾 | 键/项容量各预留 +1，`IntChildBase` 偏移按 `internal_max+1` 个键计算 |
| 验收脚本 2 分钟超时 | 10 万插入跑不完 | `TableHeap::InsertTuple` 每次从链表头扫描空槽 → O(n²) | 缓存尾页 `last_page_id_` 直接追加（O(1) 摊还）；并把缓冲池 16→1024 减少换出刷盘 |
| UNIQUE 约束未生效 | 脚本期望的唯一冲突未被拒 | Catalog 只为主键自动建索引，未覆盖 `unique` 列 | 改为 `IsPrimary() || IsUnique()` 都建索引（唯一性借索引强制） |
| `update` 报未知语句 | 脚本中的 update 失败 | 解析/执行均未实现 | 新增 `StmtType::UPDATE` + 解析 + 「删旧插新」执行 |
| 全新库保留 0 号目录页 | 递增分配器难以稳定占住 0 号页 | FetchPage 不推进分配器，会与后续 NewPage 冲突 | 给 Catalog 注入 DiskManager，用 `GetNumPages()==0` 判新库并 `NewPage` 自举 0 号页 |
| 重开库后数据丢失 | 持久化测试失败 | `~BufferPoolManager` 不刷脏页 | 新增 `FlushAllPages()`，关库前显式调用 |
| reclaim 测试 GetNumPages 失败 | 重开后文件大小不符 | `AllocatePage` 只递增计数，文件大小由 `WritePage` 决定 | 测试每次分配后写一页，模拟真实刷盘路径 |

## 五、测试与验证

### 5.1 单元测试

每个模块配一个不依赖第三方框架的 `assert` 测试，经 CMake `ctest` 统一运行，共 **13 个，全部通过**：

```
b_plus_tree_test         buffer_pool_manager_test   catalog_test
clock_replacer_test      disk_manager_test          disk_reclaim_test
execute_engine_test      index_manager_test         interpreter_test
lock_manager_test        lru_replacer_test          recovery_test
table_heap_test
```

测试设计要点举例：
- **B+ 树**：小扇出(4,4) 乱序插入触发多级分裂/借位/合并/根塌缩；2000 键关库重开验证持久化；CHAR 字典序区间。
- **Catalog**：三会话「关库/重开」验证 schema 与表数据持久、空表重建、Drop 级联删索引、主键索引持久。
- **ExecuteEngine（端到端）**：建库/表/插入(int→float 强制)/唯一冲突/where/投影/delete/update/索引/关库重开。
- **LockManager**：S-S 相容、2PL 拒新锁、wound-wait 创伤年轻者、年轻者多线程等待老者后获锁。
- **Recovery**：模拟崩溃（一个已提交事务 + 一个未提交事务），验证 redo 保留已提交、undo 回滚未提交。

### 5.2 验收脚本端到端

用一份约 10 万行的综合脚本验证（3 个数据库、建表含 `primary key`、100004 条 `insert`、
`create/drop index`、`update`、各类 `select/delete`、`show` 等）：

- 端到端跑通，约 **3.4 秒**（优化前因堆表 O(n²) 超 2 分钟）。
- `select * from account` 在 10 万行后返回正确的 100000 行；`update` 改主键后新键可查、旧键消失。
- 唯一的两处报错正是脚本注释 `-- expect primary-key and unique-key conflicts` 明确要触发的
  主键冲突与唯一键冲突，符合预期。
- `drop table` 后 `<db>.db.free` 列出数千个被回收的页号，证明空间回收生效。

## 六、AI 辅助开发说明

本项目为「AI 辅助开发」实践：每个模块先由人给出明确的实现 prompt（约定语义、接口、页布局、
测试要求），由 AI 生成实现与单元测试，再经人审查、运行测试、定位并纠正问题后提交。
各模块的实现 prompt 原文存档于 `docs/prompts/`（未收录）（00 模板，01–09 各模块）。
开发节奏为「一模块一测试一提交」，提交信息为英文，便于回溯每步的范围与验证结果。

## 七、总结与展望

**已完成**：核心需求（存储/索引/元数据/SQL/多库）与全部 Bonus（Clock 置换、空闲页回收、
2PL 锁、WAL 恢复），13 个单元测试全绿，验收脚本端到端通过。

**已知限制与可改进方向**：
- 查询执行目前以全表扫描 + 过滤为主，未把 `where` 的等值/区间条件下推到 B+ 树走索引扫描（索引已具备能力，可作查询优化）。
- B+ 树键为唯一键，因此「在非唯一列上建索引」会拒绝重复键；可扩展为非唯一索引（叶子存 RID 列表）。
- LockManager / WAL 为独立演示，未接入执行引擎的实际读写路径；可进一步把 WAL 挂到 TableHeap 写路径、
  并在事务边界做 redo/undo，实现真正的崩溃一致性。
- `DeallocatePage` 已回收页，但目录/索引页的回收仅在 DROP 时触发；可做更细粒度的空间管理（位图/分级空闲表）。

总体而言，MiniSQL 完整覆盖了一个精简 DBMS 自底向上的关键技术，并以可运行、可测试、可端到端验证的形式落地。
