# MiniSQL —— AI 辅助开发方法说明

本文记录本项目「AI 辅助开发」的具体做法，围绕五个方面展开：系统设计与模块拆分、
提示词与任务流程设计、对 AI 结果的监督与反馈、代码审查/集成/调试、测试设计与正确性验证。
所有做法均以本项目（C++17 精简 DBMS）的真实过程为依据。

---

## 1. 如何进行系统设计和模块拆分

### 1.1 先定架构，再拆模块——而不是让 AI 一次生成整个系统

AI 一次性生成大型系统极易产生「看似能跑、实则耦合混乱」的代码。本项目先由人确定**分层架构**与
**模块边界**，把系统切成职责单一、依赖单向的小模块，再让 AI 逐个实现。

采用对标 CMU 15-445 / BusTub 的自底向上分层：

```
DiskManager → BufferPoolManager(+Replacer) → TableHeap / BPlusTree
            → CatalogManager / IndexManager → DatabaseEngine
            → ExecuteEngine → Interpreter → main(REPL)
```

### 1.2 拆分原则

- **单一职责**：每个模块只解决一件事（如 `DiskManager` 只管按页读写文件，不懂记录/索引语义）。
- **单向依赖**：上层依赖下层，下层不知道上层。由此可以**按依赖顺序自底向上实现**，
  每实现一个模块，其依赖都已就绪且经过测试，避免「依赖未实现导致无法验证」。
- **接口先行**：先写好头文件（类、方法签名、模块边界、注释语义），方法体以
  `NotImplementedException` 占位。AI 实现时只填方法体，不改接口，从而**锁定契约、约束生成范围**。
- **一条铁律降低耦合**：除 `BufferPoolManager` 外任何模块都不直接碰 `DiskManager`，
  全部经 `Fetch/New/Unpin` 访问页。这条约定写进文档与注释，AI 实现各模块时一律遵守。

### 1.3 模块清单与实现顺序

| 顺序 | 模块 | 依赖 |
|---|---|---|
| 1 | DiskManager / BufferPool / Replacer | 无 |
| 2 | Value / Row / TableHeap（记录与堆表） | 缓冲池 |
| 3 | CatalogManager（元数据） | 堆表 |
| 4 | BPlusTree / IndexManager（索引） | 缓冲池；之后回填 Catalog 的索引接线 |
| 5 | Interpreter（SQL 解析） | 独立 |
| 6 | DatabaseEngine + ExecuteEngine + main（接线） | 以上全部 |
| 7 | Bonus：Clock / 空闲页回收 / Lock / WAL | 局部 |

**关键判断**：把「最大、最易出错」的 B+ 树放在元数据之后单独攻坚；把「自包含、可独立测」的解析器
和 Bonus 安排在不阻塞主线的位置。这样任何一步卡住都不会让整个系统无法推进。

## 2. 如何设计提示词、任务流程或 Agent 工作方式

### 2.1 任务流程：一模块一循环

每个模块走同一套闭环（写进项目约定，贯穿始终）：

```
① 人写实现 prompt（记录到 docs/prompts/NN-模块.md）
② AI 生成实现 + 不依赖框架的 assert 单元测试
③ 构建验证：cmake 配置 → 构建 → ctest 运行
④ 人审查、定位并纠正问题（必要时回到 ②）
⑤ 通过后单独 git commit + push（英文提交信息）
```

每个模块独立提交，使开发轨迹清晰、可回溯每步的范围与验证结果。

### 2.2 提示词设计原则

`docs/prompts/` 下 00 是模板，01–09 是各模块的真实 prompt。一条好的实现 prompt 至少包含：

- **目标文件与接口约束**：「实现 `xxx.cpp` 的全部方法，接口见 `.h`，签名不变」——防止 AI 擅改契约。
- **精确语义**：逐方法说明行为与边界。例如缓冲池 `Unpin` 的「只置脏不清除」、B+ 树「先插入后分裂」。
- **数据结构/布局**：直接给出页内布局（如堆表页头 `[next_page_id | slot_count]` + 「状态字节 + 定长记录」槽），
  避免 AI 自由发挥导致与其它模块不兼容。
- **明确的坑提示**：把已知陷阱写进 prompt。例如「`NewPage` 会把页置零，新页必须显式把 `next_page_id`
  写成 INVALID」「节点页要为临时溢出预留 1 个槽位」。
- **测试要求**：指明要覆盖的场景（如「池满全 pin 时 NewPage 返回 nullptr」「换出脏页后重读磁盘」）。

>示例（B+ 树）摘要："实现单属性单值 B+ 树……`Insert` 叶层去重、溢出分裂（叶复制首键上推、内部
>中键上推）、根分裂升高；`Remove` 下溢向兄弟借或合并、根塌缩……关键：节点页要为先插入后分裂的
>临时溢出多预留 1 个键/项的容量。"

### 2.3 Agent 工作方式

- **范围最小化**：一次只让 AI 改一个模块/一组紧密相关的文件，便于审查与回退。
- **结构化产出**：要求 AI 同时产出实现与测试，并在 prompt 文档里回填「产出要点 / 问题与纠正 / 审查与测试」。
- **复用既有约定**：让新模块「读起来像周围的代码」——注释密度、命名、错误处理（统一抛 `SqlException`）保持一致。
- **必要时人来做架构决策**：涉及跨模块签名变更（如给 `CatalogManager` 注入 `DiskManager`、
  给 B+ 树构造函数加 key 类型/尺寸）时，由人先定方案再让 AI 落地，而非让 AI 自行扩散改动。

## 3. 如何监督 AI 生成结果并进行反馈修改

### 3.1 监督手段：让"对错"可被机器和人同时判定

- **编译器即第一道关**：`-Wall -Wextra` 全开，警告当错误看待。
- **单元测试即第二道关**：每模块的 assert 测试必须全绿才算完成。
- **端到端脚本即第三道关**：用约 10 万行验收脚本压力验证真实行为。
- **人工阅读即第四道关**：逐行读懂 AI 写的逻辑，确认边界与契约。

### 3.2 反馈—修改的真实案例（本项目实际发生）

| 现象 | 监督手段发现 | 反馈/纠正 |
|---|---|---|
| B+ 树小扇出测试段错误 | ctest 段错误 | 定位为内部节点溢出键覆盖孩子数组 → 键/项各预留 +1 槽 |
| 验收脚本 2 分钟超时 | 端到端脚本计时 | 定位堆表插入 O(n²) → 缓存尾页追加 + 调大缓冲池 |
| 期望的 UNIQUE 冲突未被拒 | 端到端脚本输出比对脚本注释 | Catalog 改为对 `unique` 列也自动建索引 |
| `update` 报未知语句 | 端到端脚本报错 | 补 `StmtType::UPDATE` + 解析 + 执行 |
| 重开库数据丢失 | 持久化单测失败 | 发现 `~BufferPoolManager` 不刷脏页 → 新增 `FlushAllPages` |

### 3.3 反馈原则

- **先定位再修**：用「直接运行二进制 + 缩小输入」定位崩溃点，而不是盲改。
- **改最小面**：每次只针对一个根因修改，改完立刻重跑测试确认。
- **把教训沉淀**：发现的坑回写进对应 prompt 文档的「问题与纠正」表，避免下次重犯。

## 4. 如何审查、集成和调试生成代码

### 4.1 审查（Review）

- **契约审查**：AI 是否擅自改了接口/语义？签名是否与 `.h` 一致？
- **资源纪律审查**：每个 `FetchPage` 是否都配对 `UnpinPage`、修改过的页是否标脏？（pin 泄漏是缓冲池类系统最常见隐患）
- **边界审查**：空表/空树、首尾元素、容量临界（分裂/合并阈值）、越界索引是否处理。
- **一致性审查**：错误处理是否统一（抛 `SqlException`）、命名与注释风格是否与周边一致。

### 4.2 集成（Integration）

- **构建系统自动收集**：`CMakeLists.txt` 递归收集 `src/*.cpp` 编成静态库 `minisql_lib`，
  主程序与每个测试都链接它；`test/` 下每个 `.cpp` 自动注册为一个 ctest。新增文件**重跑 cmake 配置**即可纳入。
- **接线集中在一处**：`ExecuteEngine` 是唯一同时持有 Catalog/Index/Record 的「总线」，
  模块协作集中可见，便于排查跨模块问题。
- **跨模块改动谨慎**：集成阶段才暴露的需求（如多库层、UNIQUE/UPDATE）通过受控的小步签名调整接入，
  每步都重跑全套测试确认未破坏既有功能。

### 4.3 调试（Debug）

本项目环境为 Windows + MinGW，调试经验：

- **崩溃定位**：ctest 报 `SegFault`/`0xc0000409` 时，直接用绝对路径运行该测试二进制看输出，
  缩小到具体断言/子测试；必要时把输入规模调小（如 B+ 树用小扇出复现）。
- **区分"我的 bug"与"测试 bug"**：曾出现断言失败实为测试预期过时（新增第二张表后 `show tables` 应返回 2 而非 1），
  审查后修正测试而非乱改实现。
- **静态链接规避 DLL 问题**：MinGW 下对运行时加 `-static`，避免运行时加载到版本不匹配的 DLL（`0xc0000139`）。
- **性能问题用计时定位**：`time` 跑脚本，发现超时后回到算法层面找 O(n²)，而非微优化。

## 5. 如何设计测试并验证系统正确性

### 5.1 测试策略：分层 + 端到端

- **每模块一个不依赖第三方框架的 `assert` 单元测试**（共 13 个，`ctest` 统一运行，全部通过）。
  不引入 GoogleTest 等框架，降低构建复杂度，测试本身也成为模块用法的范例。
- **一个端到端测试**（`execute_engine_test`）：经 Interpreter + ExecuteEngine + 多库存储栈跑真实 SQL，
  覆盖建库/表/增删改查/索引/约束/投影，并含「关库—重开」的持久化验证。
- **一个真实验收脚本**：约 10 万行综合脚本压力验证整体行为与性能。

### 5.2 测试用例设计要点（举例）

- **覆盖正常 + 边界 + 异常**：如 B+ 树用**小扇出(4,4)** 以少量数据强制触发多级**分裂/借位/合并/根塌缩**，
  比大扇出更能暴露结构性 bug；并验证重复插入返回 false、删空后根塌缩为空。
- **验证持久化用"关库—重开"**：构造独立的存储栈、写入、Flush、销毁，再重新打开、加载、断言数据仍在
  （Catalog 三会话、B+ 树 2000 键、DiskManager 空闲页 `.free` 等都用此法），确保状态真的落在磁盘而非对象里。
- **并发用多线程 + 时序断言**：LockManager 用线程模拟「年轻事务被老事务阻塞 → 老者释放后获锁」。
- **恢复用"模拟崩溃"**：写一段含已提交与未提交事务的 WAL 后「崩溃」，再恢复，断言 redo 保留已提交、
  undo 回滚未提交（插入撤销、删除恢复前像）。
- **可程序化读取结果**：`ExecuteEngine` 暴露 `LastRows/LastColumns/LastAffected`，让端到端测试能用
  `assert` 校验查询结果与影响行数，而非只靠肉眼看打印。

### 5.3 正确性判定

- **机器可判定**：所有断言通过 + 退出码 0；`ctest` 汇总 13/13。
- **行为可比对**：验收脚本输出与脚本注释的预期一致——例如脚本注释 `-- expect primary-key and
  unique-key conflicts`，运行后恰好只在那两处报冲突，其余 10 万条操作结果正确，
  `select * from account` 返回 100000 行，`update` 改主键后新键可查旧键消失，`drop table` 后空闲页被回收。
- **回归保证**：每次改动后重跑全套测试 + 验收脚本，确保新功能/修复不破坏既有行为。

## 小结

本项目的 AI 辅助开发可概括为：**人定架构与契约、AI 填实现与测试、用编译/单测/端到端三道关监督、
逐模块审查纠错、一模块一提交**。AI 显著提升了编码与测试编写效率，而系统正确性来自人对架构的把控、
对关键陷阱的预判、以及对每一处生成结果的审查与回归验证。
