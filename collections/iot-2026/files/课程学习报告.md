## 一、引言

## 二、设计主题总结：桌面扫描点餐系统

### 2.1 系统目标与总体架构

桌面扫描点餐系统模拟餐厅"扫码点餐—云端下单—后厨/前台接单—语音叫号—订单状态流转"的完整闭环。系统由三个并行的顶层执行框协同工作，整体可划分为四层：

- **感知/交互层：** 通过二维码生成模块为每张餐桌生成专属点餐二维码，顾客扫码进入点餐页面；本地通过按钮输入、手动输入与 RFID 卡类型读取实现交互触发。
- **传输层：** 采用 **MQTT** 协议（MQTT 连接、MQTT 订阅、订阅队列、心跳间隔）实现订单消息的实时推送，新订单到来时以 `MQTT消息=%1` 的形式触发处理逻辑。
- **云服务/数据层：** 通过云端 WEB-API（`http://10.79.224.188:8008/api/queryDbTable.php`）访问云数据库 `diancan10`，对菜品表 `qiyu_food`、购物车表 `cart` 等进行查询与状态更新，账号信息、表名、过滤条件（如 `` `cart_order`=610000097 ``）、返回字段均作为参数化输入配置。
- **处理/输出层：** 使用 JSON 解析模块（Json 取值、Json 取元素、Json 对象）对购物车数组数据进行字段提取；通过图像显示模块呈现菜品/二维码；通过 **TTS 语音播报**（TTSSpeak，监听 UDP 22222 端口）实现"新订单""完成订单：%1(订单ID)""取消订单：%1(订单ID)"的语音叫号。

### 2.2 关键模块与工作流程

系统核心工作流程如下：

1. **下单触发：** 顾客扫码后，云端写入购物车记录；本地通过 MQTT 订阅相应主题，收到形如 `{"op":"modify","id":"610000097","status":1}` 的消息后被唤醒。
2. **数据拉取：** 调用云库读取模块，凭账号密码向 WEB-API 发起查询，返回购物车 JSON 数组（包含 `cart_food`、`cart_price`、`cart_count`、`cart_status` 等字段）。
3. **数据解析与展示：** 用 JSON 模块遍历数组、取出菜品与价格，借助格式化串（`%1,%2元;`）拼装为可读的订单详情并在界面显示。
4. **状态流转：** 操作员点击"确认订单/完成订单/取消订单"按钮，系统通过 WEB-API 回写订单 `status` 字段，并触发对应语音播报，实现订单状态在云端与本地的一致更新。

整个流程将 **MQTT 的实时性**与 **HTTP/WEB-API 的可靠查询**结合：MQTT 负责"通知有变化"，WEB-API 负责"取回准确数据"，既降低了轮询开销，又保证了数据一致性，是物联网中典型的"事件驱动 + 请求响应"混合模式。

### 2.3 拓展思路与实施方案

围绕该系统，我设想并部分验证了以下拓展方向：

- **多桌并发与会话隔离：** 利用 `cart_session`、`cart_type` 字段区分桌号与会话，使一台桌面终端可管理多桌订单。实施方案是在 MQTT 主题中加入桌号层级（如 `order/table/3`），按主题分流。
- **菜品推荐与营销：** 在云库中增加销量统计字段，查询时按销量排序返回"热销菜品"，并在二维码点餐页置顶展示。
- **库存与超时告警：** 结合课程中传感器/告警模块思路，当某菜品库存为 0 时自动置灰，并通过语音/弹窗告警；订单长时间未确认时触发提醒。
- **支付与对账闭环：** 在 `status` 状态机中增加"已支付"状态，配合云端对账接口，形成"下单—接单—完成—支付—对账"完整链路。

### 2.4 遇到的问题与解决方案

- **问题一：JSON 非法输入导致动作报错。** 调试时出现"动作 35—输入 1 不是合法的 Json 对象字符串"等错误，原因是 WEB-API 返回为空或被 URL 编码（如 `%C3%A8`）。**解决：** 在 JSON 解析前增加非空与合法性判断（"云端返回的有效 json 数据，为空时表示结果无效"），无效时跳过本次处理，避免流程中断。
- **问题二：MQTT 消息中引号与转义。** 订阅消息中单双引号混用导致字符串解析异常。**解决：** 使用平台提供的"把订阅消息中的单双引号互换后变成字符串输出"功能进行预处理。
- **问题三：语音播报。** 相同订单不播报。

## 三、未选择主题的思路与拓展：防瞌睡系统

虽然最终提交的是点餐系统，但我同样完成了**防瞌睡（疲劳驾驶检测）系统**的设计，这里描述其思路与拓展。

### 3.1 设计思路

该系统面向驾驶安全场景，核心是"采集人脸—检测眼睛—判断闭眼—累计计数—语音唤醒"。其顶层由两个执行框并行：一个负责图像采集与 AI 交互，一个负责结果处理与播报。关键模块包括：

- **相机采集：** 指定 USB 相机序号（从 0 开始），按"图片降采样倍数（默认 4）"预降采样以减小数据量。
- **人脸检测：** 返回复合句柄结果（最多 16 张人脸，为 0 表示无人脸）。
- **器官抠图与仿射变换：** 根据眼睛和鼻子位置进行标准化仿射变换，按眼距与眼—鼻距离比例校正，抠取左右眼图像句柄。
- **AI 闭眼检测：** 将眼睛图像二进制流通过 TcpTalk 发送至本地 AI 服务进程，返回 JSON 格式识别结果（变量"读取即清除"），检测到闭眼时输出为真。
- **瞌睡判定与播报：** 通过"瞌睡计数/连续闭眼计数值"判断——连续闭眼达到阈值即认定瞌睡，随后从语音集 `["专心驾驶","别睡了","快醒醒"]` 中随机选取（并保证与上次不同）进行语音播报唤醒。

### 3.2 拓展方向

- **多模态融合：** 在视觉闭眼检测基础上，引入打哈欠（嘴部张合）、点头（加速度计/姿态）等特征，降低单一指标误判。
- **分级预警：** 根据闭眼时长与频次分级，从轻度提示音到强烈语音、再到联动车窗/座椅震动。
- **个性化阈值与日志：** 记录每位驾驶员的疲劳曲线，云端存储驾驶日志，形成疲劳报告；夜间自动降低阈值。
- **边缘化部署：** 将 AI 推理迁移到边缘盒子（课程中的 EBox 设备），减少对 PC 的依赖，提升实时性与隐私性。

点餐系统与防瞌睡系统看似差异很大，但在物联网视角下高度同构：前者是"消息事件→云数据→输出反馈"，后者是"图像事件→AI 推理→语音反馈"，都体现了"感知—处理—执行"的闭环思想，这让我对物联网通用范式有了更深刻的体会。

## 四、课程收获、感想与体验

 过去我对物联网的理解停留在"传感器联网"的零散概念，而通过亲手搭建完整系统，我真正理解了感知、传输（MQTT/HTTP）、云端存储与计算、本地控制与人机交互之间如何协同，理解了"事件驱动"与"请求响应"两种通信模式的取舍。 IoTDesigner 用流程框与变量连线代替代码，极大降低了入门门槛，让我能快速验证想法；同时它也让我意识到，工程化的关键不在语言而在于对数据流、状态机与异常处理的清晰设计。无论是文本代码还是图形模块，"边界检查、超时处理、状态一致性"这些工程素养都是相通的。
